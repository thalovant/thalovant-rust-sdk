# Audit

Written after `cargo test --all-features -- --test-threads=2` passed in full on 2026-11-08 (see `MAINTENANCE_REPORT.md`), and from reading the code.

## Known issues and technical debt

1. **A 429's wait is not readable from the error.** The chat-app rate limits (`bridge_rate_limited`, `bridge_network_rate_limited`) send the wait only in the `Retry-After` header. `send_request_full` in `src/control.rs` reads that header, but only `get_with_retry_after` (used by `wait_for_admission`) keeps it; `ThalovantError::ApiResponse` (`src/errors.rs`, the `ApiResponse` variant) has no member for it, so a caller of any other method cannot know how long to wait. `tests/chat_apps.rs` (`refusals_carry_their_code_fields_and_kind`) checks the 429's status and code only.
2. **Credentials are not wiped from memory.** `SecretValue` (`src/chat_apps.rs`) holds an ordinary `String`, and the request body built by `exposed_secrets` and `create_bridge` (`src/control/bridges.rs`) is a `serde_json::Value` dropped after sending. The crate has no `zeroize` dependency; this is documented on `SecretValue`.
3. **The shared api-error vectors do not cover `fields` yet.** `produced` in `tests/api_errors.rs` records status, code, detail and problem only, as the Python reference's vectors define them. `ApiProblem::fields` and `ThalovantError::api_fields` (`src/errors.rs`) are covered by `tests/chat_apps.rs` instead.
4. **Most control-plane reads are untyped.** `list_hubs`, `get_hub`, the memory and runtime-group calls in `src/control.rs` return `serde_json::Value`; chat apps (`src/chat_apps.rs`), `OperationResource` and `DeviceLoginRequest` are the typed exceptions.
5. **Releases do not wait for the whole fleet's parity.** The consumer branch of `.github/workflows/sdk-parity.yml` runs `check-sdk-parity.py --consumer thalovant-rust-sdk` without `--release`, and `auto-release.yml` (`planned-parity`) and `publish.yml` reuse it, so a "not yet on par" state is reported but does not stop a release. See `SUGGESTIONS.md` item 5.
6. **The minimum Rust version was not built locally.** Only the current compiler was available; the `minimum-rust` CI job builds and tests on 1.88. The new code uses no feature newer than 1.88 (const `assert!` is 1.57).
7. **A browser sign-in's timeout reads as a device code's.** `browser_login` returns `ThalovantError::DeviceAuthorizationExpired` when the browser does not come back in time, and `DeviceAuthorizationDenied` for a denial, as the porting brief has every SDK reuse its device-login outcomes (`wait_and_exchange` in `src/control/browser_login.rs`). Matching on the variant is right; the fixed `Display` of the expired one says "the code expired before it was approved; call login_with_browser again", which names the device flow (`src/errors.rs`). Changing it would change device login's message. `SUGGESTIONS.md` item 8.
8. **One error variant is new, where the brief says none are.** A consent-page error such as `server_error` must be an error with no status that still carries its code (`sign_ins/another error from the consent page fails the sign-in`). `ThalovantError::Api(String)` has no code and `ApiResponse` always has a status, so `ThalovantError::BrowserLoginFailed { code }` (`src/errors.rs`) carries it and `api_code()` reads it. The enum is `#[non_exhaustive]`, so this is additive.
9. **The Windows exclusive-address path was not compiled here.** `exclusive_address_use` in `src/loopback.rs` (`#[cfg(windows)]`, `setsockopt` with `SO_EXCLUSIVEADDRUSE` from `windows-sys` 0.61) was written against the `windows-sys` 0.61.2 source in the local registry; no Windows target is installed. The CI `windows-latest` job builds it and runs the listener's tests through it. It is the crate's only `unsafe` block.
10. **Rust's control-plane requests have no timeout except a browser sign-in's.** `BROWSER_REQUEST_TIMEOUT` (10 s, `src/control/browser_login.rs`) bounds the configuration and the exchange, as the Python reference bounds every request; the reqwest client in `ControlPlane::new` (`src/control.rs`) has none, so every other call, device login's polls included, waits as long as the API takes. Left as it was: a client-wide timeout would change every other call's behaviour. `SUGGESTIONS.md` item 11.
11. **`default_device_name` runs `hostname(1)` on macOS and the BSDs.** `read_hostname` in `src/native_auth.rs` reads `/proc/sys/kernel/hostname` on Linux and Android and `COMPUTERNAME` on Windows, and otherwise spawns `hostname`, to stay free of `unsafe` and of a new dependency. It runs only when the caller names no device. Only the Linux path ran locally; `the_device_name_defaults_to_this_sdk_on_this_host` runs on the macOS and Windows CI jobs.

## Security notes

- Browser sign-in (`src/control/browser_login.rs`, `src/loopback.rs`): the listener binds `127.0.0.1` only (`the_listener_binds_ipv4_loopback_only`), on Windows with `SO_EXCLUSIVEADDRUSE`, serves at most 32 connections at once (`connections_are_bounded_and_the_callback_still_gets_through`), reaps finished ones as it waits, and logs nothing. The `state` is compared in constant time with `subtle::ConstantTimeEq`, as UTF-8 bytes, so a non-ASCII value is a 400 rather than a panic. Only RFC 6749's error codes are kept from a callback, so an `error` that repeats the state or a code never reaches an error (`callbacks/the state repeated as the error is not kept`). The code, the verifier, the state and the token never reach an error: a refused exchange's body is scrubbed before its message is built (`a_message_cut_to_length_keeps_no_part_of_a_secret`), and `without_secrets` rebuilds the error with them replaced by `[redacted]` in the message and the problem, keys included, in one pass, longest first (`scrubbing_is_one_pass_longest_first_and_leaves_its_marker_alone`); a transport failure carries nothing of the request (`a_transport_failure_during_the_exchange_carries_nothing_of_the_request`); a malformed API URL is never repeated (`an_api_url_that_cannot_be_read_is_never_repeated_in_the_error`). The API URL must be https or loopback before the configuration is asked for, every request stays on the API's origin (`no_request_leaves_the_api_origin`), and a `token_endpoint` with a colon or a broken escape is unusable. The configuration and the exchange are bounded at 10 s each (`a_stalled_configuration_is_bounded_and_auto_falls_back_to_device_login`, `a_stalled_exchange_ends_the_sign_in_and_tells_the_tab`). Dropping the sign-in closes the port at once. The exchange is never retried, since a code presented twice revokes the token the first exchange minted (RFC 9700).
- No credential reaches an error, `Debug` or JSON output: `SecretValue` has no `Display`, `Serialize` or `Deserialize` (checked at compile time by `NO_WAY_TO_PRINT_A_SECRET` in `tests/chat_apps.rs`), its `Debug` prints `<redacted>`, and `a_refused_create_never_prints_the_credentials_it_sent` checks an API that echoes the token.
- `get_bridge_avatar` reads the image as bytes (`request_bytes` in `src/control.rs`), with the same HTTPS-only rule and redirect refusal as every control-plane request, and refuses a body over 4 MiB by its `Content-Length` or while streaming (`a_picture_is_read_whole_and_never_past_its_cap`).
- A refusal of the avatar route is read at most 4 MiB too; past that it is the `ApiResponse` of its status with no problem (`read_at_most` in `src/control.rs`, covered by `a_picture_is_read_whole_and_never_past_its_cap`).
- `OperationStatus` (`src/control.rs`) is a closed public enum: an operation status the API adds later fails `ControlPlane::get_operation`. `Bridge::operation` reads such an operation as `None` (`readable_operation` in `src/chat_apps.rs`, `an_unreadable_operation_leaves_the_bridge_readable`) so the bridge stays readable; opening `OperationStatus` would break exhaustive matches and waits for a breaking release.
- Test assertions about credentials name the printed form by position rather than printing it, so a failing test cannot write a credential to the CI log (code scanning flagged the first version).

## Fixed

- **CodeRabbit on #90, and the final reference (39e31d8).** Fixed before merge, each with a test: a malformed API URL repeated in the error (`require_secure_token_exchange`, `src/native_auth.rs`); browser sign-in requests with no bound (`bounded_request`, `src/control/browser_login.rs`); a verifier prefix left in a refusal's display line cut at 200 characters (`redacted_body`); a callback `error` repeating a code or the state reaching `BrowserLoginFailed` (RFC 6749 allow-list, `classify_request`); the tab's 60 s bound, which could report a failure for a sign-in that then succeeded (dropped); finished connection tasks kept until close, and no bound on connections served at once (`wait`, `MAX_CONNECTIONS`); a callback claimed between the end of the wait and `close` losing its grace (claim and check under one lock); an `authorization_endpoint` with a host no browser can open (`real_host`); `token_endpoint` with a colon or a broken escape; `HEAD` answers with a body; an empty `device_name` replaced by the hostname; a test snapshot that dropped a non-Unicode variable. From the re-review: unbounded answer bodies (now 64 KiB, `bounded_request`); a code echoed percent-encoded (escapes in any case), or as a JSON number, left in a refusal (`hidden_forms`, `written_at`, `scrub_value`); an oversized `HEAD` answered with a body (`Head::TooLarge`); an `authorization_endpoint` such as `example.0x10` that passed the host rule but that the URL parser browsers follow refuses (`Url::parse` in `usable_authorization_endpoint`).

- **An oversized request was answered with a reset on macOS** (found by CI on #90 before merge). `serve` in `src/loopback.rs` answered a request head over 16 KiB with its 400 and closed the socket with the rest of the head unread; the kernel then reset the connection, and macOS dropped the answer before the client read it (`an_oversized_head_or_one_that_is_not_a_request_is_400_and_the_wait_goes_on` failed on `macos-latest` with ECONNRESET; Linux keeps an answer that arrived readable). Every answered connection now drains what the browser still sends, for at most 2 s and 1 MiB (`linger`), before it is closed; `an_answer_is_read_whole_although_the_browser_sent_more_than_was_read` sends bodies of up to 300 KiB and a 200 KiB head.

- **Conformance record could carry an earlier run's cases** (CodeRabbit on #64). `record()` in `tests/common/mod.rs` cleared stale shards only when `THALOVANT_CONFORMANCE_OUT` did not exist yet. The documented target, `contracts/conformance-results.json`, is committed, so it always exists. Shards are now scoped to a run, and `tests/conformance_record.rs` fails if an earlier run's shard reaches the record.

- **The 0.11.0 changelog gave the wrong quota-count ceiling** (CodeRabbit on #65, outside the diff). It said counts stop at the signed 64-bit maximum. `whole_count` in `src/refusal.rs` keeps a count only up to `MAX_COUNT`, 2^53 − 1, and reads anything larger as 0. The entry now says so. The `## 0.15.0` heading, replaced by mistake when the 0.16.0 entry was added (13d9640), is back.

- **Test-only gaps from CodeRabbit on #66 and #21** (#88). `an_empty_listing_is_answered_by_its_usual_form` and `an_empty_listing_is_not_retried_when_nearest_is_off` in `src/intents.rs` pin the usual-form retry contract: `en-CA` against a hub that loaded `en-us` keeps `languages == ["en-CA"]` and reports `listed_in == ["en-us"]`, and with `nearest: false` it lists once and reports `["en-CA"]`. The nine test servers in `src/control.rs` that took a single `read()` and then asserted on the body now read the whole request through `read_full_request`.

## Open

- **`usual_form` differs from the Python reference on two kinds of tag** (found while checking CodeRabbit on #66, by running both on the same inputs; not changed here):
  - A tag with an empty subtag: `"en-"`, `"en--US"`, `"en-US-"`. The reference returns `None` because any empty subtag ends it (`thalovant/_language.py`, `usual_form`). `src/language_matching.rs` `usual_form` returns `Some("en-us")`.
  - A language CLDR knows only through its macrolanguage: `"arb"`, `"cmn"`. The reference returns `arb-eg` / `cmn-cn`, checks the macrolanguage's likely subtags and keeps the language's own code. Rust returns `None` because `DATA.likely` has no direct entry.
  - The Go port gives the same answers as Rust on these inputs. No shared vector covers `usual_form`, so the parity gate does not see either difference.
  - Dangling singletons (`"en-u"`, `"en-x"`) already match the reference (`en-us`).
- **A `ws://` endpoint carries the access key in cleartext** (CodeRabbit on #30, outside the diff). `authorized_wss_url` in `src/transport.rs` accepts `ws://` as well as `wss://` and puts `authorization`, which is base64 of `user-agent:access_key`, in the upgrade URL's query, before Noise starts. The Python reference (`_hive.py`, "WSS endpoint must start with ws:// or wss://") and the Go port (`transport_wss.go`) accept `ws://` the same way, so refusing it only here would break parity. The access key alone does not authenticate: the Noise pre-shared key comes from the password (`derive_psk`, Argon2id), and the client key is pinned. Platform identities name `wss://` endpoints. Requiring `wss://` would be a cross-SDK decision, for every port at once. This port's HTTP transport (`require_tls_endpoint`) and MQTT (`mqtt_options_for_identity`) already refuse cleartext, as the reference's do, so WSS is the one transport that still allows it. `SUGGESTIONS.md` item 6 proposes accepting `ws://` only for a loopback destination, in every SDK at once.
- **The static key needs a filesystem with hard links** (CodeRabbit on #40). `publish_private` in `src/noise_store.rs` publishes a new `noise_key` with `fs::hard_link`, so it never replaces a key another process published first and is never seen half-written. On a filesystem without hard links (FAT32, exFAT, some network shares) the first connect fails with "atomic Noise key publication requires a filesystem supporting hard links". The Python reference does the same (`os.link` in `_noise_runtime.py`). Neither fallback is safe: `fs::rename` replaces another process's key, and `create_new` on the final path is exclusive but can leave a truncated key after a crash. The workaround is a state folder on a filesystem that supports hard links (NTFS, ext4, APFS, and most others; not FAT32 or exFAT, even on a local disk). That folder is either the identity file's own folder, since `Client::from_file` keeps the key beside it, or the one given to `set_noise_state_dir` on the transport.
- **Conformance shards on platforms without a parent process id**. Outside Unix, a run is told apart only by `THALOVANT_CONFORMANCE_RUN` or a deleted target, as before. CI records conformance on Linux.
